## HIGH
### H-1. Rate limiting is skipped for percent-encoded `/api` paths (weakens the M1 fix)
- `security/RateLimitFilter.java:70` and `security/UserRateLimitFilter.java:46`: `shouldNotFilter` tests the raw, undecoded URI (`!getRequestURI().startsWith("/api/")`).
- Scenario: `POST /ap%69/auth/login` (`%69` = `i`) or `/%61pi/...`. `StrictHttpFirewall` does not block `%69`/`%61`; Tomcat does not normalize; Spring MVC and Spring Security match the decoded path, so the request still reaches the controller while both limiter filters skip it: global, login-IP, login-username, register-IP, password-change and money/admin limits are all bypassed.
- Fix: don't gate on a prefix of the raw URI (remove `shouldNotFilter`, or use the decoded path via `ServletRequestPathUtils.parseAndCache(request).getPathWithinApplication()`); better, apply limits by matcher (LOGIN/REGISTER/MONEY/ADMIN) and `anyRequest` for the global bucket. Add tests: `/ap%69/auth/login` is limited; `/ap%69/admin/users` with a USER token gives 403.
- Confidence: prefix check confirmed in code; exploitability through real Tomcat high-plausible, not run. All tests use MockMvc, none uses an encoded path.

## MEDIUM
### M-1. Per-username login bucket bypassed by padding the body beyond 8 KB (incomplete fix of M1)
- `RateLimitFilter.java:103`: when the body prefix exceeds `MAX_LOGIN_BODY_BYTES` (8192) `usernameOf` returns null and no username bucket is charged. Boot ignores unknown JSON properties and nothing caps body size, so `{"username":"victim","password":"guess","pad":"AAAA...9KB"}` authenticates as victim while only the per-IP bucket counts it. A botnet or IPv6-rotating attacker gets 5 guesses/min per address against one account.
- Related: `{"username":123}` is not a string in the filter (null key, `RateLimitFilter.java:107`) but Jackson coerces it to "123" in the controller (a numeric legacy username would bypass the bucket).
- Fix: reject over-limit login bodies (400/413) or fail closed; treat numbers like strings or reject non-string usernames.

### M-2. Lost update: `User` entity written whole-row with no `@Version`/`@DynamicUpdate` (incomplete fix of L4 and the disable logic)
- `entity/User.java`; paths: `UserService.changePassword` (lines 83-96: loads user, two BCrypt runs ~150 ms, then flush + `bumpTokenVersion`), `updateEmail` (59-66), `setEnabled` (127-129). `token_version` is `updatable=false`, but `enabled`, `password_hash`, `email` are written from the stale snapshot.
- Scenario A: a password-change request passes the JWT filter; an admin disables the user (enabled=false, version bumped); the in-flight change flushes `enabled=true`, bumps the version and returns a fresh valid token: the user is silently re-enabled. Scenario B: the admin's `setEnabled` flush overwrites a concurrent password/email change with the old values.
- Fix: targeted `@Modifying` updates (like `bumpTokenVersion`) for password, enabled and email, or `@DynamicUpdate` plus a `@Version` column. No test covers it.

### M-3. A known username can be locked out of logging in indefinitely; the docs understate it
- `RateLimitFilter.java:~80` (`loginUsername.tryAcquire`): every attempt counts and the key is the username alone, not (IP, username). One attacker IP sending 5 attempts/min for "admin" (public in README/config) takes every refilled token, so the real user (including the admin) sees 429 almost always. Existing tokens keep working: denial of login.
- Doc error: README ~line 363 and TEST_FINDINGS.md say "slowed to about 1 attempt per 12 s, never a lockout"; that is wrong when the attacker keeps pace.
- Fix: key the bucket by (username, IP); or count only failures and let through IPs that recently authenticated as that user; or add a secondary threshold with backoff. At minimum correct the README.

## LOW / INFO
- **L-1.** Per-IP buckets are keyed on the full IPv6 address (`RateLimits.clientIp`): a /64 host rotates addresses to bypass all per-IP limits. Fix: key IPv6 on /64. Also with `trust-forwarded-headers=true`, `trusted-proxies` higher than the real proxy count makes a client-written XFF entry the key (documented); `looksLikeIp` accepts any string of hex digits, `:` and `.`.
- **L-2.** Default database credentials remain (`application.properties:4-5`, `${DB_PASSWORD:postgres}`): the M7 finding is still open (listed as "not done"). The old committed default JWT secret is still in git history; any deployment that ever used it must rotate its key.
- **L-3.** `scripts/seed-dev-data.sh` conflicts with the new rate limits: 6 logins within seconds vs login-ip capacity 5 (fails "login failed for erin", exit 1); re-runs exhaust register-ip (5/hour). Fix: sleep/retry honouring `Retry-After`, or document `app.rate-limit.enabled=false`. Known default seed password is fine for dev only.
- **L-4.** No request body size limit; `LoginRequest.username`, `TransferRequest.receiverUsername` and the admin `username` filter have no `@Size` (Jackson's 20M-char string limit applies before validation; values go to `lower(...)` in SQL). Fix: body cap + `@Size(max=50)`. Minor: `DepositRequestService.java:299` uses `toLowerCase()` with the default locale; use `Locale.ROOT`.
- **L-5.** `SchemaShapeGuard` checks names only: a non-unique or differently defined `uq_tx_owner_idempotency` would pass while the baseline skips V1. Fix: compare `pg_get_indexdef`/`pg_get_constraintdef`. Other schema gaps: no CHECK on `transactions.status`, `users.role`, `wallets.currency`; no sender<>receiver CHECK (L9 remainder); `deposit_requests.user_id` not tied to the wallet's user; no index on `deposit_requests(user_id)`; the admin "pending first" CASE sort needs a full sort; the OR history query (L10). V2 is safe on PG 11+.
- **L-6.** Admin deposit-request list has an N+1 on `user` (`DepositRequestService.listAll`, `@ManyToOne(EAGER)`): up to 100 extra selects per page. Fix: `join fetch` or LAZY + entity graph.
- **L-7.** Logging may carry PII (plausible): `GlobalExceptionHandler` logs unexpected constraint violations with the exception (pgjdbc detail includes row values); main profile leaves Hibernate `SqlExceptionHelper` on. Fix: log only SQLState + constraint name and silence that logger.
- **L-8.** Frontend: a failed logout call is swallowed (`AuthContext.signOut`; local session cleared, token stays valid server-side, user not told); `useIdempotentSubmit` keeps a key across an indeterminate outcome while the payload is unchanged, so a later deliberate identical payment in the same mounted form silently replays and shows the old transaction; 429 detection by message prefix (colour only). No XSS sinks found (no `dangerouslySetInnerHTML`, `innerHTML`, `window.open`, data-driven href/navigate; all routes fixed strings). Token is in `sessionStorage` (XSS-readable by design); no CSP in `index.html` (add at the hosting layer). A stale-token 401 cannot loop.
- **I-1.** For severity only: an admin can approve their own deposit request (no added privilege, admins can already deposit anywhere); no cancel/expiry (a user at 5 pending is stuck until an admin decides); approve does not lock the user row (approval can race a concurrent disable, small window); a disabled receiver can still be credited (L9); an admin deposit key and the owner's own transfer/withdraw key share one per-wallet namespace (409 on clash, no leak); `RateLimits.clear()`, `TokenBucketLimiter.clear()/size()` and `SchemaShapeGuard.verify*` are public test helpers in main (not exposed over HTTP); `application-dev.properties` publishes a JWT secret but binds to 127.0.0.1 unless `SERVER_ADDRESS` is overridden (a startup refusal for the dev profile on a non-loopback address would remove the footgun).
